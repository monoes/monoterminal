## RendererBridge Interface Spec

**Design:**
```rust
// Location: crates/master/src/ui/renderer_bridge.rs
use tokio::sync::mpsc;
use bytes::Bytes;
use std::sync::Arc;

pub struct RendererBridge {
    pty_rx: mpsc::Receiver<Bytes>,
}

impl RendererBridge {
    /// Attach to a session's PTY output stream
    /// Returns RendererBridge that receives Arc<Bytes> from SessionManager
    pub fn attach(
        session_manager: Arc<SessionManager>,
        session_id: SessionId,
        client_id: ClientId,
    ) -> Self {
        let (output_tx, pty_rx) = mpsc::channel(256); // 256-message buffer
        
        // Attach as local UI client to SessionManager
        session_manager.attach_client(session_id, client_id, output_tx).await;
        
        Self { pty_rx }
    }
    
    /// Receive next PTY output chunk (non-blocking)
    /// Returns None if channel closed
    pub async fn recv(&mut self) -> Option<Bytes> {
        self.pty_rx.recv().await
    }
    
    /// Try receive without blocking
    /// Returns None if no data available
    pub fn try_recv(&mut self) -> Option<Bytes> {
        self.pty_rx.try_recv().ok()
    }
}
```

**Answers to Your Questions:**

1. **Arc<Bytes> delivery?** Yes, SessionManager delivers `Vec<u8>` via mpsc, wrapped in `Bytes` for zero-copy
2. **recv() location?** Use `try_recv()` in `process_pty_output()` (non-blocking loop)
3. **Backpressure handling?** Channel buffer (256 messages) provides natural backpressure:
   - If GPU falls behind, SessionManager blocks on `send()`
   - PTY continues buffering in ConPTY kernel buffer
   - Risk: If GPU is consistently slower than PTY, memory pressure builds
   - Mitigation: Monitor channel capacity, log warnings if >80% full
