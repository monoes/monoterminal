## Protocol Schema Extensions Needed

### 1. Multi-Client Session Attach

**New message types needed:**

```protobuf
// Client → Master: Request to attach to existing session
message SessionAttachRequest {
  string session_id = 1;
  ClientInfo client_info = 2;  // Device, browser, capabilities
  uint32 scrollback_lines = 3; // How much history to send (default: 1000)
}

// Master → Client: Response with session state + scrollback
message SessionAttachResponse {
  oneof result {
    SessionState state = 1;
    Error error = 2;
  }
}

message SessionState {
  string session_id = 1;
  repeated OutputChunk scrollback = 2; // Historical output
  repeated ClientPresence attached_clients = 3; // Who else is here
  SessionMetadata metadata = 4; // Dimensions, title, cwd, etc.
}
```

**Questions:**
1. Should scrollback be compressed (zstd) in SessionAttachResponse?
2. Should we paginate scrollback for large histories (>10k lines)?
3. Do we need a "subscribe to updates" message after attach?

### 2. Presence Indicators

**New message types:**

```protobuf
// Client → Master: Heartbeat to maintain presence
message ClientHeartbeat {
  string session_id = 1;
  uint64 timestamp_ms = 2;
}

// Master → All Clients: Broadcast presence changes
message PresenceUpdate {
  string session_id = 1;
  repeated ClientPresence clients = 2;
}

message ClientPresence {
  string client_id = 1;  // UUID
  string device_name = 2;  // "John's iPhone", "Alice's Desktop"
  ClientType client_type = 3;  // WEB, MOBILE, DESKTOP
  uint64 last_seen_ms = 4;
  bool is_active = 5;  // Input focus
}

enum ClientType {
  CLIENT_TYPE_UNKNOWN = 0;
  CLIENT_TYPE_WEB = 1;
  CLIENT_TYPE_MOBILE = 2;
  CLIENT_TYPE_DESKTOP = 3;
}
```

**Questions:**
1. Heartbeat interval: 30s? 60s?
2. Should master proactively evict stale clients (no heartbeat for 2 minutes)?
3. Do we need "typing indicator" / input focus tracking?

### 3. Input Broadcasting

**Existing schema to review:**

```protobuf
message InputData {
  bytes data = 1;  // PTY input bytes
}
```

**For multi-client:**
- Do we need to tag input with client_id?
- Should master echo input to all attached clients (for collaborative awareness)?
- Or does each client get terminal output independently?

**Proposed:**

```protobuf
message InputData {
  bytes data = 1;
  string client_id = 2;  // Who sent this input (for audit/presence)
  bool broadcast = 3;  // Should master echo to all clients?
}
```

## Schema Evolution Strategy

**From ADR-004:** Schema versioning, backward compatibility

**For Phase 2:**
1. Add new message types without breaking Phase 1 clients
2. Use Protobuf `oneof` for optional Phase 2 fields
3. Version negotiation: client sends `protocol_version = 2` in hello?

**Proposed version bump:**
- Phase 1: `protocol_version = 1` (direct WebSocket)
- Phase 2: `protocol_version = 2` (adds P2P, multi-client, persistence)
