## 6 Open Questions - Resolution Status

### 1. WebRTC Signaling: Centralized vs DHT?
**ANSWERED:** Centralized (embedded in master for Phase 2 MVP)
- **Source:** ADR-011 §3.1
- **Decision:** Option A (embedded signaling in master daemon)
- **Rationale:** Simpler for MVP, no extra deployment. DHT (Kademlia) deferred to Phase 4+
- **Trade-off:** Master must be reachable for signaling (NAT issue if master behind NAT)

### 2. Directory Service: Ephemeral vs Persistent?
**ANSWERED:** Persistent (SQLite-backed)
- **Source:** ADR-011 §4.2
- **Decision:** Axum HTTP API + SQLite database
- **Rationale:** Peer registrations must survive directory service restarts; TTL-based expiry (1 hour)
- **Deployment:** Same VPS as TURN server ($5-15/month)

### 3. Session State Sync: CRDT vs OT?
**ANSWERED:** Neither - Broadcast model with FIFO input queueing
- **Source:** ADR-014 §4.1
- **Decision:** Simple broadcast (all clients see same terminal), input queue (sequential execution)
- **Rationale:** CRDT/OT overkill for sequential shell I/O; deferred input locking to Phase 3
- **Trade-off:** Input conflicts possible (queue-only, no undo)

### 4. P2P Protocol Versioning: Version Mismatch Handling?
**ANSWERED:** PeerHandshake/PeerHandshakeAck with Ed25519 signatures
- **Source:** ADR-004 §4.3
- **Decision:** min(initiator_version, responder_version) negotiation
- **Security:** Ed25519 signature prevents MITM, timestamp prevents replay attacks
- **Fallback:** If version incompatible → close DataChannel, continue via WebSocket

### 5. Compression Strategy: All Messages vs Selective?
**ANSWERED:** Selective (size threshold-based)
- **Source:** ADR-004 §2.4, ADR-011 §6.1
- **Decision:** Compress OutputData >4KB only (zstd level 1)
- **Skip:** Small messages <1KB (InputData, PresenceUpdate, etc.)
- **Ratio:** 3-5× reduction (4KB → 800-1200B)

### 6. Authentication: JWT Extension vs Separate P2P Tokens?
**ANSWERED:** Reuse Ed25519/JWT infrastructure
- **Source:** ADR-011 §7.1, ADR-014 §3.3
- **Decision:** JWT for client-server auth, Ed25519 signatures for P2P handshake
- **TURN credentials:** HMAC-SHA256, 15-minute TTL, scoped to peer_id
- **Rationale:** Leverage existing ADR-007/008 infrastructure
