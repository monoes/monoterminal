**CRITICAL FINDING #1: P2P Version Negotiation Missing**

**Problem:** ADR-004 §4 only covers client→server version negotiation. Phase 2 introduces **peer→peer** topology (WebRTC DataChannel), where clients connect directly to each other.

**Gap:** No protocol defined for:
- Which peer initiates version negotiation?
- Bidirectional downgrade (both peers must agree on same version)
- Who sends the first `AttachRequest` in P2P, or is there a separate `PeerHandshake`?

**Recommended Amendment (add to ADR-004 before approval):**

New §4.3 "P2P Version Negotiation (Phase 2)":
- Define `PeerHandshake` / `PeerHandshakeAck` message types
- Initiator sends version, responder computes `min(A, B)`, both use negotiated version
- Incompatible version rejection (e.g., v1.0 peer ↔ v2.0 peer → close connection)

**Impact if not fixed:** Phase 2 P2P launch blocked — no handshake protocol exists.

---

**CRITICAL FINDING #2: Compression Field Placement Undefined**

**Problem:** Phase 2 requires zstd compression (SRS §7.2), but ADR-004 doesn't specify where compression metadata lives.

**Options Analyzed:**
- **A: Envelope field** (`compression: CompressionType` at field 29) — self-describing, per-message control, backward-compatible
- **B: Transparent below protobuf** — zero overhead, but requires separate negotiation, breaks tooling

**Recommended Amendment (add to ADR-004 before approval):**

New §2.4 "Compression Support (Phase 2)":
```protobuf
message Envelope {
  uint64 sequence_number = 1;
  uint32 protocol_version = 28;
  CompressionType compression = 29;  // NEW: Phase 2, default NONE
  oneof message { ... }
}

enum CompressionType {
  NONE = 0;   // v1.0 compatible
  ZSTD = 1;   // Phase 2+
}
```

- Compress `oneof message` field only (leave metadata uncompressed)
- Only compress messages ≥1KB (overhead not worth it for small messages)
- v1.0 clients ignore field, default to `NONE`

**Impact if not fixed:** Phase 2 compression can't be backward-compatible — would require v2.0 breaking change.

---

**CRITICAL FINDING #3: Field Number Reservation Strategy Missing**

**Problem:** ADR-004 shows `protocol_version = 28` but doesn't explain why field 28 (leaves 2-27 unused). No documented reservation strategy → risk of future collisions.

**Recommended Amendment (add to ADR-004 before approval):**

New §2.5 "Field Number Reservation":

| Range | Purpose |
|-------|---------|
| 1 | `sequence_number` (v1.0) |
| 2-19 | Reserved for `oneof message` expansion (Phase 2 adds ~17 types) |
| 20-27 | Reserved for envelope metadata (future: encryption, tracing, QoS) |
| 28-31 | Envelope metadata (current: `protocol_version=28`, `compression=29`) |
| 32-2047 | Unreserved |

**Rationale for field 28:** Signals "this is metadata, not a message type" by being outside 2-19 range.

**Impact if not fixed:** Low risk — developers may misuse 2-27, but recoverable. Recommend fixing for clarity.
