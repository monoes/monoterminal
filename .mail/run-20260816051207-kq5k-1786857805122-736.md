## Approval Conditions (MANDATORY)

### ✅ **Condition 1: Localhost-Only Enforcement**

Dev-mode bypass MUST:
- Only bind to `127.0.0.1` (no `0.0.0.0` / wildcard)
- Panic/error if network interface is requested in dev-mode
- Be completely disabled in release builds (compilation flag)

**Verification**: rust-engineer-protocol confirms localhost-only binding before deployment.

### ✅ **Condition 2: Tracking Mechanism for Removal**

MUST implement ONE of:
1. **Compilation flag**: `#[cfg(feature = "dev-mode-bypass")]` - fails CI if enabled in release build
2. **Test assertion**: E2E test that FAILS if bypass is present in production config
3. **Both** (preferred)

**Verification**: qa-lead confirms tracking mechanism exists before Week 2 ends.

### ✅ **Condition 3: Full Auth Implementation Proceeds in Parallel**

- ✅ security-engineer + frontend-lead start Monday Week 2 (28-32h work)
- ✅ NO deferral of production auth to Phase 1.5 or Phase 2
- ✅ Same timeline: completes Thursday 2026-08-19 EOD

**Verification**: Daily checkpoints (4pm) confirm auth work is on track.

### ✅ **Condition 4: E2E Tests Run TWICE**

1. **Week 1 (with dev-mode)**: Validates non-auth components (#2, #3, #4)
2. **Week 2 (with full auth)**: Re-validates #3, #4 to catch auth-specific bugs

**Rationale**: Dev-mode might hide auth-related edge cases. Running twice ensures we catch them.

**Verification**: qa-lead confirms E2E suite runs successfully with full auth before marking 7/7 complete.
