## Failure Modes Analyzed

### Category 1: P2P Networking Infrastructure (5 scenarios)
1. **FM-001: TURN Server Unavailable** - VPS down, coturn crashed
   - Impact: P2P success drops 98% → 60-75%
   - Fallback: WebSocket relay (instant, always available)
   - Recovery: Automatic health check + retry

2. **FM-002: Directory Service Down** - Internet discovery fails
   - Impact: LAN discovery unaffected, remote users need manual config
   - Fallback: mDNS (LAN) + manual configuration
   - Recovery: Automatic DNS failover to backup

3. **FM-003: STUN Server Unreachable** - Firewall blocks UDP STUN
   - Impact: Minimal (TURN relay works)
   - Fallback: Skip STUN, proceed to TURN
   - Recovery: Multi-STUN server redundancy

4. **FM-004: WebRTC Negotiation Timeout** - Slow network, 15s timeout
   - Impact: None (WebSocket already active)
   - Fallback: Continue on WebSocket baseline
   - Recovery: Retry on next reconnect

5. **FM-005: NAT Rebinding (Mobile)** - Network switch, DataChannel breaks
   - Impact: <10s reconnect (SRS §7.2 target met)
   - Fallback: Instant WebSocket (dual-transport strategy)
   - Recovery: Background WebRTC renegotiation

### Category 2: Persistence Layer (2 scenarios)
6. **FM-006: SQLite Database Corruption** - Power loss, disk failure
   - Impact: 30s delay (backup restore), worst case: data loss
   - Fallback: WAL rollback → backup restore → fresh start
   - Recovery: Automatic backup restore (7-day retention)

7. **FM-007: Disk Full (Scrollback Storage)** - Heavy output exhausts disk
   - Impact: Scrollback truncated (oldest lines dropped)
   - Fallback: Proactive cleanup (80%), emergency purge (95%)
   - Recovery: Automatic vacuum + retention policy

### Category 3: Master Daemon (1 scenario)
8. **FM-008: Master Daemon Crash** - Panic, segfault, OOM kill
   - Impact: 5-10s reconnect, last 1-2s output lost
   - Fallback: Windows Service auto-restart → session recovery from SQLite
   - Recovery: Automatic (service manager + client auto-reconnect)

### Category 4: Collaboration Infrastructure (1 scenario)
9. **FM-009: Presence Heartbeat Timeout Cascade** - Network partition, mass eviction
   - Impact: 30-120s reconnect (exponential backoff prevents thundering herd)
   - Fallback: Rate limiting (100 conn/min) + jitter
   - Recovery: Automatic staggered reconnect

## Key Findings

**✅ Zero Single Points of Failure:**
- WebSocket baseline ensures terminal always works
- P2P infrastructure failures → graceful degradation to relay mode
- All failure modes have automatic recovery

**Data Loss Summary:**
| Failure Mode | Data Loss | Mitigation |
|--------------|-----------|------------|
| FM-001 to FM-005 | None | Fallback to WebSocket baseline |
| FM-006 (SQLite corrupt) | 0-24 hours | Daily backups, WAL recovery |
| FM-007 (Disk full) | Oldest scrollback | Automatic purge policy |
| FM-008 (Daemon crash) | Last 1-2 seconds | Write batching (100ms flush) |
| FM-009 (Heartbeat cascade) | None | Session recovery from SQLite |

**Auto-Recovery Coverage:**
- 9/9 failure modes have automatic recovery (100%)
- 7/9 require zero manual intervention
- 2/9 may need manual intervention (persistent disk corruption, scaling)
