## Bug #1: Heap Corruption (Blocks Criterion #6)

### Root Cause: Race Condition in PTY Cleanup

**The Problem:**
Concurrent access to ConPTY handles during cleanup causes `STATUS_HEAP_CORRUPTION` in `test_session_resize` (test 29/96).

**Code Flow Analysis:**

1. **manager.rs:227-248** `kill_session()`:
   - Removes session from HashMap
   - Calls `session.terminate_pty()` 
   - Waits 100ms

2. **session.rs:171-183** `terminate_pty()`:
   - **Only marks state as Terminated**
   - **Does NOT call pty.terminate()**
   - Comment says "rely on Drop for cleanup"

3. **manager.rs:100** Background task still running:
   - `pty_output_loop` task holds `Arc<RwLock<Session>>`
   - Still calling `pty.read()` in tight loop
   - Race: reading while Drop closes handles

4. **conpty.rs:336-346** `Drop` runs:
   - Calls `ClosePseudoConsole(hpc)` 
   - Calls `CloseHandle(process_handle)`
   - **While output loop is mid-ReadFile → heap corruption**

**The Incorrect Safety Comment:**
```rust
// SAFETY: Cleanup is safe even if terminate() was called
// (Windows APIs handle double-close gracefully)
```
This is **FALSE** for ConPTY under concurrent access. `ClosePseudoConsole` while another thread calls `ReadFile` on the pipe → heap corruption in ConHost.exe's internal heap.

**The Fix:**
1. Change `Session.pty` from `Box<dyn PtyBackend>` to `Option<Box<dyn PtyBackend>>`
2. Make `terminate_pty()` take ownership via `.take()` and call actual `pty.terminate()`
3. Signal output loop to stop via cancellation token
4. Await output loop exit before dropping handles
5. Remove unsafe double-close assumption

## Bug #2: Memory Leak (Blocks Criterion #7)

### Evidence: Handle Leak + Task Leak

**Symptoms:**
- Working set: +52.1% (5 min)
- Private bytes: +244%  
- **Handles: +46.3%** ← smoking gun

**Likely Root Causes:**

1. **Handle Leak** (46.3% growth proves this):
   - AsyncPipeReader/Writer Drop should close handles
   - But if `pty_output_loop` task doesn't exit, Session Arc never drops to 0
   - Handles stay open indefinitely

2. **Spawned Task Leak** (manager.rs:100, 103):
   - Each session spawns 2 background tasks:
     - `pty_output_loop` (line 100)
     - `monomind_detection` (line 103)
   - If output loop doesn't detect Terminated state quickly (100ms timeout between checks)
   - Tasks accumulate, keeping Arc alive

3. **Session Arc Leak:**
   - `kill_session` removes from HashMap
   - But output loop holds Arc until it detects SessionState::Terminated
   - Loop checks state every 100ms (line 269)
   - Between check and next read: 200ms window where session is "killed" but Arc alive

**The Fix:**
1. Use `tokio::sync::watch` channel to signal cancellation immediately (not polling)
2. Await output loop task handle join before returning from `kill_session`
3. Add drop guards to verify handle cleanup
4. Instrument with handle count tracking in tests
