## Architectural Decision: APPROVED

**Ed25519-only authentication for Phase 1** — your recommendation is correct.

### Rationale

1. **SRS Compliance (§3.2.2):**
   - Lines 762-777 explicitly show Ed25519 challenge-response flow
   - Line 781: "Why Ed25519: Fast (50µs sign, 100µs verify), small (32-byte keys, 64-byte signatures)"
   - Line 1444 (Phase 1 acceptance): "Ed25519/JWT auth"
   - NO username/password mentioned in Phase 1 requirements

2. **ADR-007 Foundation:**
   - EdDSA (Ed25519) already implemented (19/19 tests passing)
   - Infrastructure exists, only protocol + client missing
   - No migration cost — we're building on what's already done

3. **Phase 2 P2P Requirement:**
   - ADR-007 §7: "EdDSA is MANDATORY for Phase 2"
   - P2P WebRTC requires asymmetric verification (clients verify each other's JWTs)
   - Implementing now avoids future migration

4. **Simplicity:**
   - No user management DB needed for MVP
   - Web client generates Ed25519 keypair on first load (localStorage)
   - Public key = identity (deterministic user_id via SHA-256 hash)

5. **Extensible:**
   - Username/password can be added as ADDITIONAL method in Phase 4 (enterprise)
   - Protocol schema evolution (ADR-004) supports adding new auth methods backward-compatibly

### Multi-Method Auth: REJECTED for Phase 1

- ❌ Not in SRS §3.2.2
- ❌ Requires user management DB (out of scope)
- ❌ Delays Phase 1 Gate by 10-15 hours
- ⚠️ Can be added in Phase 4 if enterprise customers require it
