## Quick Answers to §12 Open Questions

**Q5: WebRTC DataChannel protocol: Reuse same Protobuf Envelope, or raw binary framing?**

✅ **REUSE Protobuf Envelope** - Same format for both WebSocket and DataChannel:

**Rationale:**
- Protocol symmetry: Client code doesn't care about transport (WebSocket vs DataChannel)
- Fallback seamless: WebRTC fails → WebSocket resume with zero protocol changes
- Schema evolution unified: Version negotiation works identically on both transports
- Debug tooling reuse: Same Wireshark dissector, same logging

**Trade-off:** ~20 bytes overhead per message (Envelope wrapper + sequence_number)
- Acceptable: Terminal output is chunked 512B-64KB (§3.1.3), 20B is <4% overhead
- Benefit: Deduplication by sequence_number works across transports (critical for late-joiner scrollback)

**Q6: P2P fallback: If WebRTC fails, automatic revert to WebSocket?**

✅ **YES - Automatic transparent fallback:**

**Flow:**
1. Client initiates WebRTC negotiation (sends WebRTCOffer over WebSocket)
2. **Keep WebSocket alive during negotiation** (don't close until DataChannel confirmed open)
3. WebRTC negotiation timeout (15s total: 10s STUN + 5s TURN) → log failure, continue on WebSocket
4. If DataChannel opens successfully → optionally close WebSocket (keep as fallback for reliability)
5. If DataChannel fails mid-session → reconnect WebSocket, resume via AttachRequest

**User experience:** No visible interruption - terminal keeps working regardless of P2P success/failure.

**Q7: ICE strategy: ice-lite vs full ICE?**

✅ **Full ICE (not ice-lite)** - ice-lite is server-only optimization, doesn't fit our model:

**Analysis:**
- **ice-lite:** Server doesn't gather candidates, only responds to client candidates (RFC 5245 §2.3)
  - Use case: Server with public IP, no NAT (e.g., Google Meet servers)
  - **Problem for MONOTERMINAL:** Master daemon is often behind home NAT (WiFi router)
  - ice-lite master can't connect if master is NATted → defeats P2P purpose

- **Full ICE:** Both sides gather candidates (client AND master)
  - Master behind NAT gathers local/STUN/TURN candidates
  - Client behind NAT gathers local/STUN/TURN candidates
  - ICE algorithm finds best path (may be master→client relay if master NAT is restrictive)

**Decision:** Full ICE required - can't assume master has public IP.

**Optimization:** Use **Trickle ICE** (already in research doc) - send candidates incrementally vs. waiting for full gathering.

**Q8: TURN credential TTL: 15-minute acceptable?**

✅ **YES - 15 minutes aligns with JWT auth_token:**

**Rationale:**
- Matches existing auth flow (JWT expires 15 min, requires refresh)
- Long enough for WebRTC negotiation (typically <30s) + connection lifetime
- Short enough to limit abuse if credentials leak
- coturn supports time-limited credentials via HMAC-based username format

**Implementation:** REST API authentication method (RFC 7635):
```
username = "timestamp:client_peer_id"  // e.g., "1723680000:ed25519_pubkey_hex"
credential = HMAC-SHA256(secret, username)
```

Master generates on-demand in WebRTCAnswer, coturn validates timestamp + HMAC.
