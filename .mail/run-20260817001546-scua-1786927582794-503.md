## Root Cause Analysis

**NOT a regression from heap corruption fix (commit 8d3259c).**

**Actual cause:** Pre-existing architectural flaw in `conpty.rs` AsyncPipeReader implementation.

### The Flaw

`AsyncPipeReader::poll_read()` (lines 113-167) calls synchronous blocking `ReadFile` directly inside `poll_read`:

```rust
fn poll_read(...) -> Poll<Result<()>> {
    let result = unsafe { ReadFile(handle, buf, &mut bytes_read, None) };
    match result {
        Ok(_) if bytes_read > 0 => Poll::Ready(Ok(())),
        Ok(_) => {
            waker.wake();  // BUG: Creates infinite spin loop
            Poll::Pending
        }
        ...
    }
}
```

**Two bugs compounded:**
1. **Spin loop bug:** When ReadFile returns 0 bytes, code called `waker.wake()` immediately and returned `Pending`, creating 100% CPU spin loop
2. **Blocking I/O bug:** ReadFile blocks when no data available, violating tokio's async contract (poll_read must not block)

**Historical context:** Test appeared to pass occasionally due to race conditions (data arriving before timeout) + spin loop consuming CPU. Never actually worked correctly.

---

## Why Not a Regression

Verified via git history:
- Heap corruption fix (8d3259c) only modified `windows.rs` (NEW FILE with proper async architecture)
- `conpty.rs` unchanged since commit 19d92c8
- Spin loop bug existed in all versions: `git show 19d92c8:crates/master/src/pty/conpty.rs | grep "waker.wake()"`

The heap corruption fix created `windows.rs` with **correct** architecture (background tasks + mpsc channels), but tests still use the old broken `conpty.rs` implementation.
