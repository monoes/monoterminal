### 3.2 HealthScheduler Daemon Integration ⚠️ DESIGN DECISION NEEDED

**Current pattern (lines 392-478):**
```rust
pub async fn start<F, Fut>(self, project_dir: &Path, callback: F) -> Result<()>
where F: Fn(HealthStatus) -> Fut
{
    let mut ticker = interval(self.interval);
    loop {
        ticker.tick().await;
        match run_doctor_check(&project_dir).await {
            Ok(health) => callback(health).await,
            Err(e) => callback(error_status).await,
        }
    }
}
```

**Issue:** This is a **blocking infinite loop** — intended for `tokio::spawn` background task.

**Question for Windows Service implementation (task-7):**

How should HealthScheduler integrate with Windows Service lifecycle?

**Option A: Spawn on Service Start (Recommended)**
```rust
// In Windows Service OnStart handler:
let health_handle = tokio::spawn(async move {
    scheduler.start(project_dir, |health| async move {
        // Send health to UI via broadcast channel
    }).await
});

// In OnStop handler:
health_handle.abort();
```

**Option B: Manual Tick (Alternative)**
```rust
// Call run_doctor_check() directly on:
// - Service startup (validate monomind present)
// - Dashboard request (on-demand check)
// - Timer (daily, via Windows Task Scheduler external trigger)
```

**Recommendation:** **Option A** aligns better with SRS §2.4.3 daily scheduler requirement.

**Action Required:**
- **BEFORE task-7 (Windows Service) starts:** Confirm HealthScheduler integration pattern
- **CREATE ADR-005:** Document daemon background task lifecycle (spawn vs manual tick)

## 5. Protocol Schema Evolution Readiness: ⚠️ NEEDS ADR

**Current state:**
- Protocol v1 defined in `proto/monoterminal/v1/messages.proto` ✅
- No versioning metadata in Envelope (only sequence_number) ⚠️
- No documented evolution policy ⚠️

**SRS Requirement (§3.1.1):**
> "ensuring backward/forward compatibility (schema evolution) before any wire-format change ships"

**Gaps:**
1. No version field in Envelope to detect client/server version mismatch
2. No ADR documenting: "When is a new field safe? When is it breaking?"
3. No test suite for schema evolution scenarios

**Recommendation:**

**Before Phase 2 ships (P2P networking adds new message types):**

1. **ADD version negotiation** (non-breaking now, while in Phase 1):
   ```protobuf
   message Envelope {
     uint64 sequence_number = 1;
     uint32 protocol_version = 28;  // New field (defaults to 0 for old clients)
     oneof message { ... }
   }
   ```

2. **CREATE ADR-006: Protocol Evolution Policy**
   - Safe additions: optional fields, new message types (ignored by old clients)
   - Breaking changes: field number reuse, required field changes (require major version bump)
   - Compatibility matrix: what versions can interoperate?

3. **ADD schema evolution tests** (protocol crate):
   ```rust
   #[test]
   fn test_old_client_ignores_new_fields() { ... }
   
   #[test]
   fn test_new_server_handles_old_client_messages() { ... }
   ```

**Action:**
- **NON-BLOCKING** for Phase 1 MVP (single client + single server version)
- **BLOCKING** for Phase 2 (P2P means client/server version skew is real)

**Assignee:** principal-architect (ADR-006) + rust-engineer-protocol (version field + tests)

### 6.2 No Socket Activation (As Expected) ✅

> "Windows has no launchd/systemd-style socket activation, so Phase 1 accepts an always-running service"

**Implication:** Service starts on boot, listens immediately (no lazy activation)

**Action:** Confirm this trade-off in ADR-005 (daemon lifecycle)

### 6.3 TLS Certificate Loading ✅
- TLS config loads from `certs/server.crt` and `certs/server.key` (server/tls.rs:25-30)
- Paths are configurable (TlsConfig::new allows override)

**Recommendation for Windows Service:**
- Default paths should use `%ProgramData%\MONOTERMINAL\certs\` (not relative paths)
- Add to ADR-005: document cert path resolution order (env var → config file → default)

### 6.4 Logging Integration ⚠️

**Current:** Uses `tracing` crate (good choice) ✅

**Gap:** No Windows Event Log integration yet

**SRS §7.1 implies:** Service should log to Windows Event Log (standard for Windows Services)

**Recommendation:**
- Phase 1 MVP: File logging to `%ProgramData%\MONOTERMINAL\logs\` is acceptable
- Phase 2+: Add `tracing-windows-event-log` subscriber for production deployments

**Action:** Document in ADR-005 (non-blocking for MVP)
