### 1. GPU Rendering Approach — ✅ APPROVED

**Review of `docs/architecture/gpu-pipeline-implementation-plan.md`:**

The wgpu approach is architecturally sound and aligns with SRS §2.1.1 requirements:
- ✅ WGSL shaders (vertex + fragment) - correct choice over legacy GLSL
- ✅ 4096×4096 R8Unorm atlas - appropriate for ~2000 unique glyphs with LRU eviction
- ✅ Guillotine bin-packing - industry-standard allocator, used by Alacritty/WezTerm
- ✅ DirectX 12 backend (wgpu automatic) - correct for Windows 10 1809+ (SRS §1.2)
- ✅ 60 FPS target (16.67ms budget, 8ms GPU render) - within DirectX 12 capabilities

**Critical enhancement identified in shader review (Option A):**

`docs/architecture/shader-review-notes.md` correctly identifies that the prototype shader lacks **per-cell background color support**. rust-backend-lead's recommendation to add `bg_color: vec4<f32>` to vertex input (Option A) is **architecturally mandatory** for terminal emulation:

- **Why mandatory:** ANSI escape sequences like `\e[42;31m` (red on green) require per-cell bg colors, not just transparent-where-alpha=0. Without this, Phase 1 cannot pass acceptance (unusable for most terminal workflows).
- **Cost acceptable:** +16 bytes/vertex = +23KB vertex buffer for 80×24 grid (negligible vs 16MB atlas).
- **Single-pass rendering:** Cleaner than 2-pass (backgrounds first, glyphs second), better performance.

**Architectural decision:** Implement Option A (add `bg_color` to vertex struct) **before** Phase 1 GPU pipeline ships. This is a 2-hour addition per the plan, well within the 8-12h total budget.

**Linear sampler (antialiasing):** Also approve switching from Nearest to Linear filter mode per shader review notes. No shader code change needed (sampler config is CPU-side), improves readability, standard practice for modern terminals.

**No other objections.** The 8-12h timeline is realistic if environment issues are resolved (blocked on cargo PATH fix per your dispatch).

**Minor recommendation 1: Monomind message versioning**

`DashboardRequest.command` field uses strings (`"status"`, `"agents"`, `"memory"`). Consider an enum for type safety:

```protobuf
enum DashboardCommand {
  STATUS = 0;
  AGENTS = 1;
  MEMORY = 2;
  // ... future commands
}

message DashboardRequest {
  DashboardCommand command = 1;  // was: string command
  map<string, string> params = 2;
}
```

**Impact:** Non-breaking if added now (pre-release). Breaking change if added post-Phase 1 release.

**My call:** Low priority for Phase 1 gate (strings work fine), but **file an issue for Phase 2** if dashboard commands grow beyond 3-4 variants.

**Minor recommendation 2: Protocol changelog discipline**

ADR-004 requires `docs/PROTOCOL_CHANGELOG.md` and `docs/PROTOCOL_VERSIONS.md` (§6). I don't see these files in the repo yet.

**Action:** rust-engineer-protocol should create these **before Phase 1 release** per ADR-004 implementation plan (Phase 1, steps 4). This is documentation, not code — 1 hour work, critical for schema evolution tracking post-release.

**Minor recommendation 3: Obsolete `envelope.proto` cleanup**

ADR-004 §1 states:
