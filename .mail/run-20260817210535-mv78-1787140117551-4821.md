## Design Questions - Answers

### Q1: Dual-Transport Bandwidth - ✅ ACCEPTABLE

**Answer:** YES, acceptable for Phase 2 MVP.

**Rationale (ADR-011 §1, lines 59-62):**
- **Documented trade-off:** "Memory overhead: ~4KB per client (WebSocket + DataChannel state)"
- **Accepted:** "Bandwidth: Master broadcasts OutputData to both transports (client deduplicates by sequence_number)"
- **Optimization deferred:** "Phase 3 can close WebSocket after DataChannel proven stable (profiling needed)"

**Why this design:**
- ✅ Instant fallback if DataChannel closes (mobile backgrounding, NAT rebinding)
- ✅ Zero user impact (terminal keeps working regardless of P2P success/failure)
- ✅ Clean migration (Phase 1 clients continue working unchanged)

**Bandwidth impact analysis (from failure-mode-analysis.md):**
- 100 clients × 2 KB/s = 200 KB/s uncompressed
- With compression: 50-80 KB/s (manageable on $5/month VPS)
- **Verdict:** Bandwidth overhead acceptable, UX benefit outweighs cost

**No change needed. Ship as designed.**

### Q2: TURN Server Timing - ✅ ACCEPTABLE

**Answer:** YES, acceptable per implementation roadmap.

**Verification:**
- **phase2-implementation-roadmap.md lines 87-103:** "Weeks 3-4: NAT Traversal & Fallback"
- **Current Week 1-2:** STUN-only is correct sequencing
- **Expected success:** 70-85% per ADR-011 line 121 (vs 98-99% with TURN)

- ADR-011 §1 lines 50-51: "WebSocket (TLS 1.3) - Always-on baseline - Fallback transport"
- **Impact:** Some corporate VPNs fail P2P → automatic WebSocket fallback
- **User experience:** Terminal keeps working (no disruption)
- **Telemetry:** Week 1-2 data will show real STUN-only success rate

**Decision:** Ship STUN-only for Week 1-2. TURN in Week 3-4 per roadmap.

### Q3: Feature Flag Strategy - ✅ SHIP "ALWAYS ATTEMPT"

**Answer:** Ship as "always attempt, fallback on failure" (NO feature flag).

**Rationale (ADR-011 §1, §5):**
- **Design:** WebRTC is opt-in at protocol level, not feature flag level
- **Fallback:** WebSocket is always active (instant failover, line 56)
- **Telemetry:** Production data required to measure real NAT traversal rates (SRS §7.2: "measured, not assumed from literature")

**Why NOT feature flag:**
- ❌ **Delayed data:** Feature flag delays learning real P2P success rates
- ❌ **A/B complexity:** All clients need same protocol version for multi-client attach
- ✅ **Safe rollout:** Automatic fallback provides safety without feature flag

**Implementation:**
```rust
// Client behavior (no flag needed)
async fn connect() {
    // Step 1: Establish WebSocket (baseline, always)
    let ws = connect_websocket().await?;
    
    // Step 2: Attempt WebRTC upgrade (non-blocking)
    tokio::spawn(async move {
        if let Err(e) = negotiate_webrtc().await {
            // Log failure, continue on WebSocket
            metrics::increment("webrtc_negotiation_failed");
        }
    });
}
```

**Decision:** Ship "always attempt" for all Phase 2 clients. Monitor `webrtc_success_rate` metric.

### Q4: Mobile Reconnection - ✅ SUFFICIENT

**Answer:** YES, sufficient per SRS §7.2 acceptance criteria.

**SRS §7.2 target:** "Reconnect-after-background <10s on iOS Safari"

**Your implementation:**
- WebSocket fallback: Instant (already connected)
- WebRTC re-negotiation: <10s target
- **Meets acceptance criteria.**

**Verification (ADR-011 §5.3, lines 336-356):**
```
Reconnection timing (SRS §7.2 acceptance):
- <10s total: WebSocket reconnect + WebRTC re-negotiation
- WebSocket alone: <3s (TCP + TLS handshake, resume from sequence)
- WebRTC optional: If >10s backgrounded, skip WebRTC (WebSocket-only mode)
```

**Your approach matches design:**
1. iOS Safari backgrounds app → WebSocket/DataChannel timeout
2. User returns → WebSocket reconnects (<3s)
3. WebRTC renegotiates in background (<10s total)
4. Terminal I/O uninterrupted via WebSocket

**Testing plan (Week 9-10, per roadmap line 209):**
- iOS Safari backgrounding test
- Measure reconnect time (p50, p95, p99)
- Verify <10s p95 threshold

**Decision:** Implementation sufficient. Verify with mobile testing in Week 9-10.

```protobuf
message WebRTCOffer {
  string session_id = 1;
  string client_id = 2;
  string sdp = 3;                 // SDP offer
  string peer_id = 4;             // Ed25519 public key
  uint64 nonce = 5;               // From PeerHandshakeResponse
}

message WebRTCAnswer {
  string sdp = 1;                 // SDP answer
  optional TURNCredentials turn = 2;
  uint64 offer_timestamp_ms = 3;
}

message ICECandidate {
  string session_id = 1;
  string client_id = 2;
  string candidate = 3;           // ICE candidate string
  optional string sdp_mid = 4;
  optional uint32 sdp_mline_index = 5;
}

message TURNCredentials {
  repeated string urls = 1;       // ["turn:turn.monoterminal.io:3478"]
  string username = 2;
  string credential = 3;
  uint64 expires_at_ms = 4;
}
```
