### 🔍 Why EdDSA (Not HS256)

**HS256 (Symmetric):**
```
Server: HMAC bytes (sign + verify)
Client: No verification (trusts server)
Problem: Can't share verification without sharing signing capability
```

**EdDSA (Asymmetric):**
```
Server: Private bytes (sign only)
Client: Public bytes (verify only, can't forge)
Benefit: Clients can verify without forging
```

**Phase 2 P2P Requirement:**
- Clients connect directly to each other (WebRTC DataChannel)
- Client A signs JWT, Client B verifies with A's public material
- HS256 fails this (symmetric = can't share verification safely)
- EdDSA works (asymmetric = public material shareable)

**Conclusion:** EdDSA is mandatory for Phase 2. Implementing now avoids migration.
