## Topics to Cover

### 1. HealthScheduler Integration Pattern ✅ (Decision Made)

**eng-director recommends OPTION A** (I agree):

**Pattern:** Spawn on Service Start (tokio background task)

```rust
// Windows Service OnStart handler:
let health_handle = tokio::spawn(async move {
    let scheduler = HealthScheduler::new(); // 24h interval
    scheduler.start(&project_dir, |health| async move {
        // Send health status to broadcast channel → UI clients
        broadcast_tx.send(health).await.ok();
    }).await
});

// Service OnStop handler:
health_handle.abort();
```

**Rationale:**
- ✅ Matches SRS §2.4.3 daily scheduler requirement
- ✅ Clean tokio integration (no Windows Task Scheduler external dependency)
- ✅ Graceful shutdown via abort() on service stop

**Your input needed:**
- Any Windows Service lifecycle concerns with this pattern?
- Should we add health check result caching to avoid npx spam?

### 2. Certificate Path Resolution Order

**Current state:**
- TLS config defaults: `certs/server.crt`, `certs/server.key` (relative paths)
- TlsConfig::new() allows override (good)

**Question:**
For Windows Service installation, what path resolution order makes sense?

**Proposed:**
1. **Environment variable** `MONOTERMINAL_CERT_DIR` (highest priority)
2. **Config file** `%ProgramData%\MONOTERMINAL\config.toml`
3. **Default** `%ProgramData%\MONOTERMINAL\certs\`

**Your input needed:**
- Is `%ProgramData%` the right location for Windows Service data?
- Should we support `%LOCALAPPDATA%` for non-admin installs?

### 3. Logging Strategy (Phase 1 MVP)

**Current:** `tracing` crate (good choice)

**Question:** Windows Event Log integration?

**Proposed for Phase 1:**
- ✅ File logging: `%ProgramData%\MONOTERMINAL\logs\monoterminal.log`
- ✅ Rotation: 10MB max, 5 files kept (via `tracing-appender`)
- ⏳ Windows Event Log: Deferred to Phase 2 (requires `tracing-windows-event-log` crate)

**Rationale:**
- File logging is sufficient for MVP debugging
- Event Log requires admin permissions to create event source (complicates installer)
- Can add Event Log later without changing log call sites (tracing subscriber swap)

**Your input needed:**
- Any strong opinion on Event Log for Phase 1?
- Should installer pre-create log directory?

### 4. Graceful Shutdown Pattern

**Current:** Not yet implemented (expected in task-7)

**Question:** What shutdown sequence do you prefer?

**Proposed:**
```rust
// Receive Windows Service Stop signal
service_stop_signal.recv().await;

// 1. Stop accepting new connections
listener.close();

// 2. Send graceful shutdown to all sessions
for session in sessions {
    session.send_graceful_shutdown(timeout: 5s).await;
}

// 3. Abort background tasks
health_handle.abort();
rendering_handle.abort();

// 4. Flush logs
tracing::flush();

// Exit
```

**Your input needed:**
- Timeout duration for graceful session shutdown?
- Should we wait for PTY processes to exit, or kill them?
