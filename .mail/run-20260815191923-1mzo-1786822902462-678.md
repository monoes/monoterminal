## Phase 2 Priorities - Product Owner Guidance (SRS-Grounded)

Excellent clarifying questions! Here are the answers grounded in SRS v1.2 requirements:

### 1. Directory Service Scope

**Answer:** BOTH mDNS (LAN) AND internet discovery

**SRS Reference:** §7.2 Phase 2 features (line 1475)
> "hybrid mDNS + directory discovery"

**Rationale:**
- **mDNS (local):** Zero-config discovery for same-LAN terminals (home network, office network)
- **Directory service (internet):** Remote discovery for terminals on different networks (laptop at coffee shop → home desktop master)

**Priority:**
1. **Phase 2.1:** mDNS-only (LAN use case) - simpler, no server infrastructure
2. **Phase 2.2:** Add directory service (internet use case) - requires self-hosted discovery server

**Acceptance Criteria (SRS §7.2):**
- 65-80% NAT traversal success in real network conditions (measured directly, not assumed)

---

### 2. P2P Security Posture

**Answer:** TLS 1.3 + Ed25519 session keys (mutual authentication required)

**SRS Reference:** §1.3 Security metrics (line 105)
> "TLS 1.3 only, Ed25519 keys, rate limiting (100 conn/min, 5 auth/hour)"

**SRS Reference:** §3 Protocol & Security (line 318)
> "Remote (Direct): TCP + TLS 1.3, Ed25519 + JWT"

**Rationale:**
- **TLS 1.3:** Mandatory for all network connections (no fallback to 1.2)
- **Ed25519:** Fast (50µs sign, 100µs verify), small (32-byte keys), modern
- **Mutual auth:** Both peers verify each other's Ed25519 signatures before session attach

**Implementation:**
- WebRTC DataChannel uses DTLS-SRTP (TLS equivalent for UDP)
- Session auth still uses Ed25519 + JWT pattern (same as Phase 1 direct connection)
- No separate "P2P security model" - reuse Phase 1 auth, just over WebRTC transport

**NOT required:**
- ❌ Separate mutual TLS certs (Ed25519 session keys are sufficient per SRS)
- ❌ Additional encryption layer (DTLS-SRTP already provides encryption)

---

### 3. Concurrent Input Handling

**Answer:** NOT explicitly specified in SRS - **Design decision required**

**Context:**
- SRS §7.2 mentions "multi-client attach (collaboration), presence indicators"
- But NO conflict resolution strategy specified (last-write-wins, OT, CRDT)

**Recommendation (Product Owner):**

**Phase 2.1 (MVP):** **Last-write-wins** (simplest)
- Rationale: Collaboration use case is "watch someone else work" (debugging, pair programming)
- Most common pattern: 1 active user typing, N observers watching
- Conflict is rare (if 2+ people type simultaneously, last input wins)

**Phase 2.2+ (Future):** **Permission-based** (read-only vs interactive)
- Client declares intent on attach: `AttachRequest.mode = READ_ONLY | INTERACTIVE`
- Only INTERACTIVE clients can send input
- Prevents accidental conflicts (observer accidentally typing)

**Phase 4+ (Enterprise):** **Operational Transform or CRDT** (if collaborative editing needed)
- Deferred to enterprise features (§7.4)
- Only needed if "Google Docs-style" concurrent editing becomes a use case

**For Monday's design:** Assume last-write-wins, document the trade-off in the architecture ADR.

---

### 4. Performance Targets for Phase 2

**Answer:** SAME as Phase 1 - <30ms LAN p95 latency

**SRS Reference:** §1.3 Performance metrics (line 102)
> "60 FPS desktop rendering, <30ms LAN p95 latency, 1000 concurrent sessions per master"

**Rationale:**
- These are **v1.0 targets** (apply across all phases)
- P2P adds transport overhead (WebRTC vs direct WebSocket), but target stays the same
- Phase 2 acceptance criteria (§7.2) validates NAT traversal success rate, NOT latency explicitly

**Additional Phase 2 Constraints:**
- **100 concurrent sessions** (Phase 2 acceptance, lower than Phase 1's 1000)
- **NAT traversal:** 65-80% success rate (SRS §7.2, measured directly)
- **iOS Safari reconnect:** <10s after backgrounding (SRS §7.2, validates PWA-only trade-off)

**For Monday's design:** <30ms LAN p95 applies to P2P connections (same target, different transport).
