### 2. Certificate Path Resolution ✅ AGREE with MODIFICATIONS

**Proposed order:** ✅ GOOD
1. Environment variable `MONOTERMINAL_CERT_DIR`
2. Config file `%ProgramData%\MONOTERMINAL\config.toml`
3. Default `%ProgramData%\MONOTERMINAL\certs\`

**My input:**
- ✅ **%ProgramData% is CORRECT** for Windows Service (requires admin, runs as SYSTEM/LocalService)
- ✅ **%LOCALAPPDATA% support: YES, for development mode**
  - Service mode → %ProgramData% (admin install)
  - Console mode (--console flag) → %LOCALAPPDATA% (user install)
  
**Recommendation:** Dual-mode support
```rust
fn get_cert_dir(service_mode: bool) -> PathBuf {
    // 1. Environment variable (override)
    if let Ok(cert_dir) = env::var("MONOTERMINAL_CERT_DIR") {
        return PathBuf::from(cert_dir);
    }
    
    // 2. Service mode vs Console mode
    if service_mode {
        // %ProgramData%\MONOTERMINAL\certs\
        PathBuf::from(env::var("ProgramData").unwrap())
            .join("MONOTERMINAL").join("certs")
    } else {
        // %LOCALAPPDATA%\monoterminal\certs\
        PathBuf::from(env::var("LOCALAPPDATA").unwrap())
            .join("monoterminal").join("certs")
    }
}
```

**Rationale:** Development workflow shouldn't require admin rights

### 4. Graceful Shutdown Pattern ✅ GOOD with MODIFICATIONS

**Proposed sequence:** ✅ CORRECT order

**My input on questions:**

**Q: Timeout duration for graceful session shutdown?**
- **Recommendation: 10 seconds** (not 5s)
  - Gives PTY processes time to flush output
  - Users might have running processes (builds, downloads)
  - 10s is Windows Service default shutdown timeout

**Q: Wait for PTY processes or kill them?**
- **Phase 1: KILL after timeout** (simpler, acceptable for MVP)
  - Try graceful shutdown (send Ctrl+C to PTY process)
  - Wait up to 10s
  - Force kill any remaining processes
  
- **Phase 2: Make configurable**
  - Let users choose: graceful-wait vs force-kill
  - Useful for long-running builds

**Modified shutdown sequence:**
```rust
// Receive Windows Service Stop signal
service_stop_signal.recv().await;

// 1. Stop accepting new connections
listener.close();

// 2. Send graceful shutdown to all sessions (Ctrl+C to PTY)
let shutdown_tasks: Vec<_> = sessions.iter()
    .map(|session| session.send_shutdown_signal())
    .collect();

// 3. Wait up to 10s for graceful shutdown
tokio::select! {
    _ = futures::future::join_all(shutdown_tasks) => {
        info!("All sessions shut down gracefully");
    }
    _ = tokio::time::sleep(Duration::from_secs(10)) => {
        warn!("Timeout waiting for sessions, force killing");
        for session in sessions {
            session.force_kill().await;
        }
    }
}

// 4. Abort background tasks
health_handle.abort();
rendering_handle.abort();

// 5. Flush logs
tracing::flush();

// Exit with code 0 (clean shutdown)
std::process::exit(0);
```

### 5. Service Control Interface (My Addition)

**Question:** How should users control the service?

**Options:**
- A: Built-in commands: `monoterminal --install`, `--uninstall`, `--start`, `--stop`
- B: sc.exe only (Windows built-in)
- C: Services.msc GUI only

**Recommendation: OPTION A** (built-in commands)
- Better UX than raw sc.exe
- Can validate configuration before install
- Can show helpful error messages

**Implementation:**
```bash
# Install service (requires admin)
monoterminal --install

# Uninstall service (requires admin)
monoterminal --uninstall

# Start/stop (or use Services.msc)
monoterminal --start
monoterminal --stop

# Run in console mode (dev/debug, no service)
monoterminal --console
```
